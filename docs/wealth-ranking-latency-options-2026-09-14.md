# 재물운 5분 제한, 동일 5명 실측과 응답 형식

## 확인된 실행 설정 차이

사용자가 제시한 작업 `a5a369ce-2298-49c6-8b0e-35ecb8964984`는 20:50:30 KST 접수, 20:55:30 실패했다. 처리 약 300.493초, DB reason은 READING_FAILED다. 이 작업의 개별 Kie 실패 로그가 보관되지 않아 HTTP 524인지 단정할 수 없다.

점검 당시 localhost:8080은 원본 checkout의 PID 44241에서 실행 중이었다. 원본 소스/빌드는 v7, reasoningEffort=null, .env 제한 600000이었다. 직전 변경인 v8/low/180초는 Codex 작업 복사본에만 있었다. 따라서 해당 화면 요청은 최적화한 설정의 실측이 아니다.

## 같은 5명으로 다시 수행한 실제 요청

작업에 저장된 chartId 5개가 사용자가 제시한 목록과 일치하는지 확인했다. 저장된 원국을 재계산하지 않고 소유권 확인 → KASI → fortuneteller → Kie → 출력 검증을 실행했다. 검증 과정은 기존 작업을 변경하거나 새 결과를 DB에 저장하지 않았다.

| 단계 | 첫 검증 | 두 번째 검증 | 세 번째 검증 |
| --- | ---: | ---: | ---: |
| 데이터 준비 전체 | 185ms | 265ms | 185ms |
| Kie 헤더 대기 | 55,039ms | 6,047ms | 11,487ms |
| Kie 전체 | 55,463ms | 6,817ms | 12,155ms |
| 파이프라인 결과 | content JSON 오류, 약 55.65초 | 성공, 7.143초 | 성공, 12.525초 |

모두 v8/low, 비스트리밍, 같은 31,500 bytes 입력이었다. 전체 4주 분석 4명, 시간 미상 부분 분석 1명이다. 첫 검증의 KASI 대조는 119ms, fortuneteller는 4ms였다. 음양력 날짜 대조는 matched이나 절입 대조는 no_data/unavailable가 섞여 있어 공식 절기 대조가 모두 완료됐다고 표현하면 안 된다. 이 상태는 서버에 남기고 결과 안내에 반영한다.

Kie 대기시간이 주된 병목이다. 응답이 없어 기다리는 동안 Kie 내부의 대기열/모델/다른 공급자 중 어느 부분이 지연됐는지는 앱에서 관측할 수 없다. 성공 사례가 5분 이내 처리 가능함을 보여주지만, 모든 호출의 성공을 보장하지는 않는다.

## 응답 JSON

실제 성공 응답은 OpenAI 호환 envelope다. `choices[0].message.content`에 또 하나의 JSON 문자열이 있다. 즉 바깥 응답 JSON과 안쪽 풀이 JSON을 별도로 읽어야 한다. 현재 adapter는 OpenAI envelope와 문서에 제시된 Gemini candidates envelope를 모두 지원한다.

첫 검증은 HTTP 200/351 bytes를 받은 후 model_output_json에서 실패했다. 그 원문은 당시 보관되지 않아 정확한 content를 복구하지 못했다. 이후 두 번은 정상 응답 원문을 확보했다. 첫 오류가 코드 블록·일반 설명·제공자 오류 문구 중 무엇인지는 미확정이다.

전송 포장으로 인한 불필요한 실패를 줄이기 위해 BOM/앞뒤 공백, 전체를 감싼 JSON 코드 블록, 한 번 더 문자열화된 JSON을 정상화한다. JSON 일부만 추출하거나 누락 값을 만들어 채우지는 않는다. 거절·잘린 응답·툴 호출·부정확한 참여자/근거는 계속 거절한다. 이 보강이 첫 형식 오류의 원인을 확정해서 고쳤다는 의미는 아니다.

원문은 로컬 `.local/wealth-ranking-debug/<jobId>/`에만 보관한다. 운영 로그에는 원문 대신 completionChars와 completionFormat을 추가해 다음 실패가 어떤 형태인지 구별한다. 이 폴더는 Git에서 제외한다.

## 시간을 줄이는 방법 비교

| 방법 | 기대 효과 | 판단 |
| --- | --- | --- |
| 실제 서버에 v8/low 반영 | 불필요한 지시·메타데이터와 추론 부담 감소 | 최우선. 작업 복사본과 실행 서버의 차이를 먼저 해소 |
| 완성된 JSON의 포장 정상화 | 코드 블록 등 때문에 재요청하는 경우를 줄임 | 적용. 추가 AI 호출 없음 |
| 같은 차트 조합·프롬프트 버전의 완료 결과 재사용 | 반복 요청에서 AI 호출 생략 | 다음 후보. 최초 요청은 빨라지지 않으며 소유권/삭제/버전 정책 필요 |
| 스트리밍 | 첫 응답 시점 관측과 점진적 전달 | 후보. 최종 JSON 완료 시간을 보장하지 않으며 SSE 파서와 중단/잘림 검증 필요 |
| 공급자/모델 전환 또는 Google 직접 연결 | Kie 중계 계층을 분리 비교할 수 있음 | 지연이 계속될 때 우선 비교. 새 인증키 및 출력 품질 검증 필요 |
| 서버에서 순위 결정 후 AI는 문장만 작성 | AI의 비교 부담과 순위 변동 감소 | 효과 가능성이 크지만 재물 평가 규칙 자체를 새로 설계해야 함. 현재 정확성/시간 미상 정책을 유지하려면 별도 검토 필요 |
| 순위와 문장 생성을 두 AI 호출로 분리 | 각 호출 작업이 단순해짐 | 직렬 대기와 비용/실패 지점이 늘어 현재는 보류 |
| KASI 캐시 확대·워커 동시성 증가 | 대조/큐 대기 감소 | 이번 병목에 효과 작음. KASI는 이미 캐시·요청 병합·병렬 조회를 하며 준비 전체가 0.3초 미만 |
| 무조건 재시도·여러 모델 동시 요청 | 일부 일시적 오류를 피할 수 있음 | 비용과 중복 호출을 늘리므로 적용하지 않음 |

[Google의 thinking 문서](https://ai.google.dev/gemini-api/docs/generate-content/thinking)는 low를 지연 감소용 옵션으로 설명한다. [Kie 문서](https://docs.kie.ai/market/gemini/gemini-3-8-flash-openai)는 reasoning_effort와 스트리밍을 안내한다. 옵션 지원과 실제 지연 보장은 별개다.

## 적용 정책

전체 작업은 접수부터 최대 300초다. `.env`의 WEALTH_RANKING_TIMEOUT_MS는 300000으로 설정하며, 실제 AI 요청에는 남은 작업 시간에서 저장 여유 5초를 뺀 제한을 사용한다. 대기·준비에 시간이 들면 AI 예산도 줄어든다. DB 장애나 워커 중단 때 상태 기록 시점까지 정확히 300초로 보장할 수는 없다.

서버 시작 로그 wealth_ranking_provider_configured에서 promptVersion=v8, reasoningEffort=low, providerTimeoutMs=300000, jobTimeoutMs=300000을 확인한다. 오래 기다리면 30초마다 kie_request_waiting에 waiting_response_headers 또는 waiting_response_body와 경과시간이 나온다.

공개 API/DB schema 변경은 없으며 기존 결과를 계속 조회한다. 현재 변경으로 새 migration은 필요 없다. PostgreSQL 통합 테스트는 계정의 임시 스키마 생성 권한 부족 때문에 미실행이며, 단위/e2e에서 마감시각·늦은 응답·출력 검증을 확인한다.

## 실제 서버 반영과 검증

2026-09-14 21:19 KST에 원본 프로젝트에도 변경 사항을 반영하고 개발 서버를 다시 시작했다. 시작 로그에서 `wealth-ranking-v8`, `reasoningEffort=low`, `providerTimeoutMs=300000`, `jobTimeoutMs=300000`을 확인했다. 21:20 KST에 localhost:8080/health는 HTTP 200으로 응답했다.

원본 프로젝트에서 lint, 단위 테스트 261개, e2e 테스트 99개, build가 통과했다. 코드 변경 이후 동일한 검사를 반복하기 위해 실행 서버를 다시 빌드할 필요는 없다. 실제 Kie 검증 세 건은 앞 표에 기록한 별도의 진단 실행이며, 기존 실패 작업의 DB 상태를 성공으로 바꾸지 않았다.
